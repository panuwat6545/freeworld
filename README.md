# Freeworld

เกมจำลองระบบนิเวศ พัฒนาเป็นเฟสตาม `docs/work-instruction.md`

## เฟส 1 — โลกและทรัพยากร (เสร็จแล้ว)

สร้างแผนที่โลกแบบ grid ขนาด 40x40 ช่อง โดยแต่ละช่องอาจมีจุดทรัพยากรธรรมชาติหนึ่งชนิด
(ไม้ / น้ำ / แร่ / อาหาร) ซึ่งจะค่อยๆ งอกกลับมาใหม่ตามเวลา (tick) จนกว่าจะเต็มปริมาณสูงสุดของจุดนั้น
ยังไม่มีตัวละครหรือ AI ในเฟสนี้

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/world/
  resource-types.js    -> ชนิดทรัพยากรและค่าตั้งต้น (ปริมาณสูงสุด, อัตราการงอก)
  resource-node.js      -> จุดทรัพยากร 1 จุด: เก็บเกี่ยว (harvest) และงอกใหม่ (update)
  random.js              -> PRNG แบบ seed ได้ ใช้สร้างโลกซ้ำแบบเดิมได้เพื่อ debug/test
  grid.js                 -> ตาราง 40x40 ของช่องแผนที่
  world-generator.js      -> สุ่มวางจุดทรัพยากรลงบน grid
  world.js                -> รวมทุกอย่างเข้าด้วยกัน มี update(deltaTicks) ให้เวลาผ่านไป
  demo.js                  -> สคริปต์สาธิตรันจริง แสดงผลการเก็บเกี่ยว/งอกใหม่ทาง console
```

### วิธีทดสอบ

```bash
npm install        # ไม่มี dependency ภายนอก แต่รันไว้เผื่อ setup ในอนาคต
npm run demo:world # รันสาธิตเฟส 1 ทาง console
npm test           # รัน unit test (ใช้ node:test ที่มากับ Node.js)
```

`npm test` ตรวจสอบว่า:
- โลกถูกสร้างเป็น grid ขนาด 40x40 จริง
- การสร้างโลกด้วย seed เดียวกันได้ผลลัพธ์ซ้ำเดิม (deterministic)
- ทรัพยากรงอกใหม่ตามอัตราที่กำหนดและไม่เกินค่าสูงสุด
- การเก็บเกี่ยว (harvest) ไม่ได้มากกว่าที่มีอยู่จริง
- `World.update` ทำให้ทรัพยากรที่ถูกเก็บจนหมดค่อยๆ งอกกลับมา

## เฟส 2 — ตัวละครและระบบความคิด (Utility AI) (เสร็จแล้ว)

ตัวละครแต่ละตัวมีตำแหน่งบน grid และค่าความต้องการ (needs) 4 อย่าง: หิว (hunger), พลังงาน (energy),
ที่อยู่ (shelter), สังคม (social) อยู่ในช่วง 0-100 ทุก tick ค่าเหล่านี้จะลดลงเองตามอัตรา decay ที่ตั้งไว้
(หิวลดเร็วที่สุด สังคมลดช้าที่สุด) แล้วระบบ Utility AI จะคำนวณว่า need ไหน "เร่งด่วนที่สุด" (ค่าต่ำสุด)
และให้ตัวละครเลือกทำพฤติกรรมที่ตอบสนอง need นั้นโดยอัตโนมัติ — เป็นสูตรคำนวณล้วนๆ ไม่มีการเรียก LLM
หรือ API ภายนอกต่อตัวละครแต่อย่างใด

พฤติกรรมทั้ง 4 แบบ:
- **หิวต่ำ** -> เดินเข้าหาจุดทรัพยากร "อาหาร" ที่ใกล้ที่สุด แล้วเก็บกินเมื่อถึง
- **พลังงานต่ำ** -> หยุดพัก ฟื้นพลังงานบางส่วนต่อ tick (เฟส 3 เพิ่มโบนัสเมื่อพักใกล้ที่พักที่สร้างไว้แล้ว)
- **ที่อยู่ต่ำ** -> เดินเข้าหาจุดทรัพยากร "ไม้" แล้วสะสมไว้ใน inventory (เฟส 3 นำไม้ที่สะสมนี้ไปสร้างที่พักจริง)
- **สังคมต่ำ** -> เดินเข้าหาตัวละครอื่นที่ใกล้ที่สุด แล้วฟื้นค่า social เมื่ออยู่ติดกัน

การเดินใช้วิธี greedy ทีละช่อง (8 ทิศ) เข้าหาเป้าหมายตรงๆ ยังไม่มี pathfinding หลบสิ่งกีดขวาง

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/characters/
  needs-config.js    -> อัตราการ decay และค่าคงที่ของแต่ละพฤติกรรม (ฟื้นพลังงาน, ปริมาณเก็บเกี่ยว ฯลฯ)
  character.js         -> Character entity: position, needs, inventory, decayNeeds()
  movement.js            -> stepToward (เดินทีละช่องแบบ greedy), ระยะห่างแบบ Chebyshev
  target-finder.js        -> หาจุดทรัพยากร/ตัวละครอื่นที่ใกล้ที่สุดบน grid
  behaviors.js              -> พฤติกรรมทั้ง 4 แบบ (seekFood, rest, gatherWood, socialize)
  utility-ai.js              -> หา need ที่เร่งด่วนที่สุดและสั่งให้ตัวละครทำพฤติกรรมที่ตรงกัน
  demo.js                     -> สคริปต์สาธิตตัวละคร 5 ตัว แสดง needs/behavior เปลี่ยนตามเวลา
```

### วิธีทดสอบ

```bash
npm run demo:characters # รันสาธิตเฟส 2 ทาง console ดู needs และพฤติกรรมของตัวละคร 5 ตัวตามเวลา
npm test                 # รวม unit test ของเฟส 1 และเฟส 2 (ใช้ node:test)
```

`npm test` ของเฟส 2 ตรวจสอบว่า:
- needs ลดลงตามอัตรา decay ที่ตั้งไว้ และไม่ต่ำกว่า 0
- ระบบ Utility AI เลือก need ที่เร่งด่วนที่สุด (ค่าต่ำสุด) ได้ถูกต้อง รวมถึงกรณีค่าเท่ากันที่ต้องตัดสิน
  ด้วยลำดับความสำคัญ
- การแม็ป need -> พฤติกรรมถูกต้องครบทั้ง 4 แบบ
- การเดิน (`stepToward`) ขยับเข้าหาเป้าหมายถูกทิศทางทุกกรณี (แนวตรง/แนวทแยง/ถึงเป้าหมายแล้ว)
- พฤติกรรมแต่ละแบบทำงานจริงแบบ end-to-end: เดินเข้าหาเป้าหมายแล้วเก็บเกี่ยว/พัก/เข้าสังคมเมื่อถึง

## เฟส 3 — ระบบสร้างสิ่งของ (Building/Crafting) (เสร็จแล้ว)

เพิ่มสูตรสิ่งก่อสร้าง (blueprint) อย่างน้อย 1 แบบ คือ "ที่พัก" (shelter) ซึ่งต้องใช้ไม้ 10 หน่วย
พฤติกรรม "เก็บไม้" จากเฟส 2 ยังทำงานเหมือนเดิม (สะสมไม้เข้า `inventory.wood`) แต่ตอนนี้ Utility AI
จะตรวจก่อนทุก tick ว่า need ที่เร่งด่วนที่สุดคือ shelter และ inventory มีไม้ครบสูตรหรือยัง — ถ้าครบแล้ว
จะเลือกพฤติกรรมใหม่ "สร้างที่พัก" แทนการเดินไปเก็บไม้เพิ่ม โดยวางสิ่งก่อสร้างลงบน grid ที่ตำแหน่งปัจจุบัน
ของตัวละครทันที แล้วหักไม้ออกจาก inventory ตามสูตร

นอกจากนี้พฤติกรรม "พัก" (energy ต่ำ) จากเฟส 2 ก็ถูกอัปเกรด: ถ้าตัวละครอยู่ใกล้ (ระยะ Chebyshev ≤ 3)
ที่พักที่เคยสร้างไว้ (ของตัวเองหรือตัวละครอื่นก็ได้) จะฟื้นพลังงานเร็วขึ้นกว่าพักเฉยๆ ตามค่าที่ตั้งไว้ใน blueprint

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/building/
  blueprints.js         -> สูตรสิ่งก่อสร้าง (ตอนนี้มี "shelter": ใช้ไม้ 10, โบนัสฟื้นพลังงาน + ระยะใกล้)
  structure.js            -> Structure entity: ชนิด, ตำแหน่ง, ใครสร้าง, สร้างที่ tick ไหน
  crafting.js               -> hasEnoughResources / canBuild / build (หักทรัพยากร + วางสิ่งก่อสร้างลงโลก)
  structure-finder.js        -> หาสิ่งก่อสร้างชนิดที่กำหนดที่ใกล้ตำแหน่งที่สุด / ตรวจว่าอยู่ในระยะใกล้หรือไม่
  demo.js                      -> สคริปต์สาธิตตัวละครเก็บไม้จนครบแล้วสร้างที่พักสำเร็จ
```

ไฟล์ที่แก้ไขเพิ่มจากเฟส 2 (อยู่ในขอบเขตของงาน เพราะต้องเชื่อม building เข้ากับ utility-ai และ world):
- `src/characters/behaviors.js` — เพิ่มพฤติกรรม `build_shelter`, ปรับ `rest` ให้เช็คที่พักใกล้เคียง
- `src/characters/utility-ai.js` — เช็คว่าครบสูตร blueprint หรือยังก่อนเลือกระหว่างเก็บไม้กับสร้างที่พัก
- `src/world/world.js` — เพิ่ม `world.structures` เก็บสิ่งก่อสร้างทั้งหมดที่ถูกสร้างในโลก

### วิธีทดสอบ

```bash
npm run demo:building # รันสาธิตเฟส 3 ทาง console: ตัวละครเก็บไม้จนครบ 10 แล้วสร้างที่พักสำเร็จ
npm test                # รวม unit test ของเฟส 1-3 (ใช้ node:test)
```

`npm test` ของเฟส 3 ตรวจสอบว่า:
- `hasEnoughResources` / `canBuild` ตรวจสูตร blueprint ถูกต้องตามจำนวนที่มีจริงใน inventory
- `build` หักทรัพยากรออกจาก inventory และวางสิ่งก่อสร้างลงบนโลกที่ตำแหน่งตัวละครได้ถูกต้อง
  รวมถึงคืนค่า `null` และไม่หักอะไรเมื่อทรัพยากรไม่พอ
- `findNearestStructure` / `isNearStructureType` หาสิ่งก่อสร้างที่ใกล้ที่สุดและตรวจระยะได้ถูกต้อง
- ผ่าน `utility-ai` ตัวละครเลือกพฤติกรรม `build_shelter` เองอัตโนมัติทันทีที่เก็บไม้ครบสูตร
- พฤติกรรม "พัก" ฟื้นพลังงานเร็วขึ้นจริงเมื่ออยู่ใกล้ที่พัก เทียบกับพักเฉยๆ ที่ไม่มีที่พักอยู่ใกล้
- `buildShelter` ฟื้นค่า need `shelter` กลับขึ้นมาจริงหลังสร้างสำเร็จ และไม่วนกลับไปเก็บไม้/สร้างซ้ำทันที
  (กันบั๊กเดิมที่ shelter ค้างต่ำสุดตลอดกาล — ดูหัวข้อถัดไป)

### บั๊กที่พบภายหลังและแก้ไขแล้ว: shelter need ไม่เคยฟื้นหลังสร้างที่พัก

ระหว่างรัน `scripts/long-run.js` (เครื่องมือสำรวจ จำลอง 30 ปีในเกม ไม่ใช่ demo ของเฟสไหน) พบว่า
`buildShelter()` ใน `src/characters/behaviors.js` เรียก `build()` หักทรัพยากรสำเร็จ แต่ไม่เคยเพิ่มค่า
`character.needs.shelter` กลับขึ้นมาเหมือนที่ `seekFood`/`rest`/`socialize` ฟื้น need ของตัวเอง ผลคือ
shelter ค้างต่ำสุดตลอดกาลทันทีที่แตะ 0 ครั้งแรก กลายเป็น need เร่งด่วนที่สุดแทบทุก tick (เพราะ tie-break
ใน `getMostUrgentNeed` เลือกตาม priority order) ทำให้ตัวละครวนลูปเก็บไม้ -> สร้างที่พักไม่หยุด ไม่เคยไป
กิน/พัก/เข้าสังคมเลยตลอดการจำลอง

**แก้ไข:** เพิ่ม `NEEDS_CONFIG.SHELTER_RESTORE_AMOUNT = 100` ใน `needs-config.js` แล้วให้ `buildShelter()`
ฟื้นค่า `needs.shelter` กลับเต็ม (clamp ที่ 100) ทันทีที่ `build()` สำเร็จ

**เหตุผลที่เลือกฟื้นเต็ม 100 แทนฟื้นบางส่วน:** ต่างจาก hunger/energy/social ที่ฟื้นแบบค่อยเป็นค่อยไปตาม
ปริมาณของพฤติกรรมที่ทำ (กินอาหารเป็นสัดส่วนกับที่เก็บได้, พักฟื้นทีละ tick, คุยฟื้นทีละ tick — ทำได้ต่อเนื่อง
หลายรอบ) การสร้างที่พักเป็นเหตุการณ์ทีเดียวจบ (discrete one-time event) พอสร้างเสร็จตัวละครก็ "มีที่อยู่แล้ว"
ทันที ไม่มีเหตุผลเชิงเกมที่จะให้ยัง "ขาดที่อยู่บางส่วน" ค้างอยู่หลังสร้างเสร็จ การฟื้นเต็ม 100 จึงสมเหตุสมผล
กว่าการฟื้นบางส่วน

**ผลตรวจสอบหลังแก้ (รัน `npm run long-run` ซ้ำ 30 ปี ตัวละคร 9 ตัว บน config เดิมทุกอย่าง):**
- flag "ตัวละครที่ AI น่าจะมีปัญหา" หายไปหมดทุกช่วงเวลา (ปีที่ 5, 10, 15, 20, 25, 30) จากเดิมที่ติด flag
  ครบทั้ง 9 ตัวทุกช่วงเวลา
- ค่าเฉลี่ย need ทั้ง 4 ตัวอยู่ในช่วง 80-93 ตลอดการจำลอง (จากเดิม shelter/social ค้างที่ 0.0 ตลอด)
- ที่พักสร้างสำเร็จสะสมลดลงจาก 9,935 หลัง เหลือ 4,119 หลัง (ตลอด 30 ปี, ตัวละคร 9 ตัว) ลดลงกว่าครึ่ง —
  ตัวเลขนี้ยังดูสูงเมื่อเทียบกับสามัญสำนึก (~15 หลัง/ตัวละคร/ปี) แต่สาเหตุไม่ใช่บั๊กนี้แล้ว เป็นเพราะต้นทุน
  สร้างที่พักถูกมาก (ไม้แค่ 10 หน่วย เท่ากับเก็บไม้ครั้งเดียว) เทียบกับอัตรา decay ของ shelter (0.6/tick)
  ซึ่งเป็นเรื่องการ tune สมดุลเกม (blueprint cost / decay rate) ไม่ใช่บั๊ก logic — นอกขอบเขตงานแก้บั๊กรอบนี้
  จึงไม่ได้แก้ รายงานแยกไว้เผื่อผู้ดูแลโปรเจกต์ต้องการปรับสมดุลเกมต่อในอนาคต

### ปรับสมดุลเกม (balance) รอบถัดมา: ลดจำนวนที่พักที่สร้างเกินจำเป็น

ต่อจากบั๊กด้านบน ผู้ดูแลโปรเจกต์สั่งให้ปรับ 2 ค่าใน config เพื่อลดจำนวนที่พักสะสมให้สมเหตุสมผลขึ้น
(เป้าหมาย ~3-5 หลัง/ตัวละคร/30 ปี จากเดิม ~15 หลัง/ตัวละคร/**ปี**):

1. `BLUEPRINTS.shelter.cost.wood` ใน `blueprints.js`: เพิ่มจาก 10 เป็น **25** หน่วย
2. `NEEDS_CONFIG.DECAY_RATE.shelter` ใน `needs-config.js`: ตามคำสั่งเริ่มต้นให้ลดลง ~40% จาก 0.6 (เหลือ
   0.36) ก่อน

**ผลตรวจสอบรอบแรก (คำสั่งเริ่มต้น เพิ่มต้นทุนไม้ + ลด decay 40%):** รัน `scripts/long-run.js` แล้วได้
ที่พักสะสม 2,210 หลัง (~8.2 หลัง/ตัวละคร/ปี) — ลดลงจากเดิมเกือบครึ่ง แต่ **ยังห่างจากเป้าหมายมาก**
(เป้า ~3-5 หลัง/ตัวละคร/**ตลอด 30 ปี** คือรวมทั้งหมดควรอยู่ราว 27-45 หลัง ไม่ใช่หลักพัน) เพราะกลไกเลือก
พฤติกรรมของเกม (`getMostUrgentNeed`) เลือกจาก need ที่ "ต่ำสุด ณ ขณะนั้น" เทียบกันทุก tick ไม่ใช่เทียบกับ
เกณฑ์คงที่ ดังนั้นแค่ลด decay 40% ยังไม่พอที่จะทำให้ shelter "ชนะ" การแข่งขันเป็น need เร่งด่วนน้อยลงมาก
พอ ต้นทุนไม้ที่เพิ่มก็ช่วยได้แค่ยืดเวลาต่อรอบการสร้างหนึ่งครั้ง (ต้องเก็บไม้นานขึ้นก่อนสร้างได้) ไม่ได้ลด
"ความถี่ที่ shelter กลายเป็น need เร่งด่วน" โดยตรง

**ปรับเพิ่มเติมเอง (ตามข้อ 4 ที่ให้ตัดสินใจเองถ้าตัวเลขยังไม่สมเหตุสมผล):** ทดลองลด
`DECAY_RATE.shelter` ลงอีกหลายระดับแล้ววัดผลจริงด้วย `scripts/long-run.js` ทุกครั้ง (ตาราง; ต้นทุนไม้คงที่
ที่ 25 ตลอด):

| DECAY_RATE.shelter | ที่พักสะสม (30 ปี) | เฉลี่ย/ตัวละคร | flag "AI มีปัญหา" |
|---|---|---|---|
| 0.36 (ลด 40% ตามคำสั่งเริ่มต้น) | 2,210 | ~245.6 | ไม่ขึ้น |
| 0.05 | 401 | ~44.6 | ไม่ขึ้น |
| 0.01 | 123 | ~13.7 | ไม่ขึ้น |
| 0.003 | 38 | ~4.2 (ตรงเป้าที่สุด) | **ขึ้น** — #3, #5 (hunger,energy,social) |
| 0.0035 | 45 | ~5.0 | **ขึ้น** — #3 (hunger,energy,social) |
| 0.005 | 59 | ~6.6 | ไม่ขึ้น |
| 0.006 | 69 | ~7.7 | ไม่ขึ้น |

พบว่าเมื่อลด decay ของ shelter ต่ำมากจนแทบไม่แข่งเป็น need เร่งด่วนเลย (0.0035 ลงไป) จะไปโผล่บั๊ก/ปัญหา
**อื่น** ที่มีอยู่ก่อนแล้วแทน: มีตัวละคร 1-2 ตัว (ขึ้นกับตำแหน่งเริ่มต้นจาก seed) ที่ hunger/energy/social
ค้างต่ำกว่า 20 ต่อเนื่องเกิน 3 ปี — เข้าใจว่าเดิมทีบั๊ก shelter (หรือแม้แต่ตอนที่ decay ยังสูง) บังคับให้ตัวละคร
เดินวนไปมาเก็บไม้บ่อยๆ ซึ่งบังเอิญพาตัวละครกลุ่มนี้ผ่านแหล่งทรัพยากรอื่นไปด้วย พอ shelter เลิกแข่งบ่อย
ตัวละครกลุ่มนี้เลยมีโอกาสไปติดวนลูป/ไปไม่ถึงทรัพยากรอื่นแทน **นี่คือปัญหาแยกต่างหาก ไม่เกี่ยวกับงานปรับ
สมดุลรอบนี้ และไม่ได้แก้ในรอบนี้ (นอกขอบเขต) รายงานแยกไว้ให้ผู้ดูแลโปรเจกต์พิจารณาต่อ**

**ค่าสุดท้ายที่เลือกใช้: `DECAY_RATE.shelter = 0.005`** (ลดจากเดิม 0.6 ประมาณ 99%, มากกว่าคำสั่งเริ่มต้นที่ขอ
40% มาก) เพราะ:
- ให้ที่พักสะสม 59 หลังตลอด 30 ปี (~6.6 หลัง/ตัวละคร) ใกล้เคียงเป้าหมาย 3-5 หลัง/ตัวละครมากที่สุดในบรรดา
  ค่าที่ **ไม่ทำให้เกิด flag "AI มีปัญหา"** ขึ้นมาใหม่
- มีระยะห่างปลอดภัยจากจุดที่เริ่มโผล่ปัญหาอื่น (0.0035) พอสมควร (~43% สูงกว่าจุดวิกฤต) ไม่ใช่ค่าที่ตัดพอดี
  ขอบเหว
- เลือกเอนเอียงไปทาง "ปลอดภัย ไม่โผล่บั๊กใหม่" มากกว่า "ตรงเป้าเป๊ะ" เพราะเป้าหมาย 3-5 หลัง/ตัวละคร
  เป็นตัวเลขอ้างอิงคร่าวๆ ("ประมาณ") ในโจทย์ ไม่ใช่ hard requirement เท่ากับ "flag ต้องไม่ขึ้น" ซึ่งเป็น
  hard requirement ชัดเจนกว่า

**ผลตรวจสอบสุดท้าย (cost=25, decay=0.005):**
- ที่พักสะสม 30 ปี = 59 หลัง (~6.6 หลัง/ตัวละคร/30 ปี) เทียบกับก่อนแก้บั๊กทั้งหมด (9,935 หลัง) ลดลง ~168 เท่า
- flag "AI มีปัญหา" ไม่ขึ้นเลยทุกช่วงเวลา (ปีที่ 5, 10, 15, 20, 25, 30)
- ค่าเฉลี่ย need ผันผวนมากขึ้นกว่ารอบก่อน (hunger/energy/social ลงไปแตะ ~33-50 ในบางปี) เพราะ shelter
  ไม่ได้ "แย่ง" ความสนใจของ AI บ่อยเหมือนเดิมอีกแล้ว ทำให้ 3 need ที่เหลือแข่งกันเองถี่ขึ้น — แต่ไม่มีตัวไหน
  ค้างต่ำกว่า 20 ต่อเนื่องเกิน 3 ปีจริง (ตรวจสอบผ่าน flag แล้ว) จึงยังถือว่าปกติ ไม่ใช่สัญญาณ AI มีปัญหา

## เฟส 4 — ระบบสังคม/ถิ่นฐาน (เสร็จแล้ว)

> ตอนแรกข้ามเฟส 4 ไปทำเฟส 5 ก่อน (ดูหมายเหตุด้านล่าง) เพราะเฟส 4 ถูกระบุไว้ว่า "ถ้าต้องการ" (optional)
> ภายหลังผู้ดูแลโปรเจกต์อัปเดต `docs/work-instruction.md` เพิ่มนิยามเฟส 4 ให้ชัดเจนแล้วสั่งให้เริ่มทำจริง

เพิ่มระบบถิ่นฐาน (Settlement) ที่เกิดขึ้นเองจากตำแหน่งการสร้างที่พัก ไม่ต้องมีใครสั่งตั้งใจ ตามนิยามในข้อ 3
ของ `docs/work-instruction.md`:
- **ถิ่นฐาน (Settlement)** — กลุ่มที่พักที่อยู่ใกล้กันในระยะ `CLUSTER_RADIUS` จัดกลุ่มแบบ transitive
  (A ใกล้ B และ B ใกล้ C ถือเป็นถิ่นฐานเดียวกัน แม้ A กับ C จะไกลกันเกิน radius ก็ตาม)
- **สมาชิก** — ตัวละครที่ `homeSettlementId` (field ใหม่บน `Character`) ชี้มาที่ถิ่นฐานนั้น ตัดสินจากว่า
  ตัวละครไปพัก (`rest`) หรือสร้างที่พัก (`build_shelter`) ใกล้ที่พักไหนบ่อยสุดในหน้าต่างเวลาหนึ่ง
- **ผู้นำ** — สมาชิกที่สร้างที่พักในถิ่นฐานนั้นมากที่สุดชนะ ถ้าเท่ากันให้คนที่ `homeSettlementId` เป็นถิ่นฐาน
  นี้นานที่สุดชนะ (เตรียมไว้ให้เฟส 8 ใช้ต่อ)
- **การขยายเผ่าพันธุ์** — ตัวละคร 2 ตัวในถิ่นฐานเดียวกันที่อยู่ใกล้กัน + social สูงต่อเนื่องนานพอ เกิด
  ตัวละครใหม่ 1 ตัวในถิ่นฐานเดียวกัน จำกัดด้วย cooldown ต่อคู่ + เพดานประชากรรวม

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/society/
  settlement-config.js  -> ค่าคงที่ทั้งหมด (CLUSTER_RADIUS, interval, threshold ต่างๆ) แยกไฟล์เดียว
  settlement.js          -> Settlement entity: structureIds, memberIds, leaderId
  settlement-detector.js  -> สแกน world.structures จัดกลุ่มเป็นถิ่นฐาน (union-find) คำนวณใหม่เป็นระยะ
                              หรือทันทีที่มีที่พักใหม่ รักษา identity ของถิ่นฐานเดิมไว้ข้ามรอบคำนวณ
  home-tracker.js          -> ติดตามว่าตัวละครพัก/สร้างใกล้ที่พักไหนบ่อยสุด แล้วอัปเดต homeSettlementId
  leadership.js              -> computeLeader/computeAllLeaders เลือกผู้นำตามกฎ + tie-break
  reproduction.js              -> ReproductionSystem ตรวจเงื่อนไขขยายเผ่าพันธุ์ + คูลดาวน์ + เพดานประชากร
  society-system.js              -> SocietySystem รวมทั้งหมดไว้จุดเดียว เรียก .update(world, characters, tick)
  demo.js                          -> สคริปต์สาธิตถิ่นฐานก่อตัว/ผู้นำเปลี่ยน/เกิดลูกใหม่
```

ไฟล์ที่แก้ไขเพิ่ม (อยู่ในขอบเขตงาน เพราะต้องผูก Character เข้ากับถิ่นฐานตามข้อ 3 ของสเปก):
- `src/characters/character.js` — เพิ่ม field `homeSettlementId`, `homeSettlementSinceTick`, `bornAtTick`
  (อัปเดตโดย `home-tracker.js`/`reproduction.js` เท่านั้น ไม่ได้ตั้งค่าตอนสร้างตัวละคร)

**ไม่ได้แก้** `behaviors.js`/`utility-ai.js` เลย — `home-tracker.js` สังเกต `character.currentBehavior`
(ที่ตั้งไว้แล้วโดย utility-ai) และตำแหน่งจากภายนอกแทน เพื่อไม่ให้ characters module ต้องรู้จักเรื่องถิ่นฐาน

### วิธีทดสอบ

```bash
npm run demo:society # สาธิต 3 เรื่อง: ถิ่นฐานก่อตัวเอง, ผู้นำเปลี่ยนมือ, ตัวละครใหม่เกิดจากการขยายเผ่าพันธุ์
npm test              # รวม unit test ของเฟส 1-4 (ใช้ node:test)
```

`npm test` ของเฟส 4 (`tests/society.test.js`) ตรวจสอบว่า:
- `SettlementDetector` จัดกลุ่มที่พักตามระยะถูกต้อง ทั้งกรณีธรรมดาและแบบ transitive (A-B-C ต่อกันเป็นทอด)
- `SettlementDetector` ไม่คำนวณซ้ำโดยไม่จำเป็นถ้าไม่มีอะไรเปลี่ยนและยังไม่ครบ interval แต่คำนวณทันทีถ้ามี
  ที่พักใหม่เกิดขึ้น (กันบั๊กที่เจอจริงตอนพัฒนา — ดูหัวข้อ "บั๊กที่พบระหว่างพัฒนา" ด้านล่าง)
- `SettlementDetector` รวม 2 ถิ่นฐานเดิมเข้าด้วยกันถูกต้องเมื่อมีที่พักใหม่มาเชื่อม พร้อมย้าย memberIds และ
  ปรับ `homeSettlementId` ของตัวละครที่เกี่ยวข้อง
- `HomeSettlementTracker` อัปเดต `homeSettlementId` ถูกต้องตามที่พักที่ใช้บ่อยสุด และไม่นับตัวละครที่ไม่ได้
  พัก/สร้างหรืออยู่ไกลเกินระยะ
- `computeLeader` เลือกผู้นำถูกต้องตามกฎ ครอบคลุมทุกระดับ tie-break (สร้างเท่ากัน -> อยู่นานกว่า ->
  character.id น้อยกว่า)
- `ReproductionSystem` เกิดตัวละครใหม่ถูกต้องเมื่อครบเงื่อนไข ไม่เกิดถ้าไม่มีถิ่นฐานเดียวกัน หยุดเมื่อถึง
  เพดานประชากร มี cooldown ต่อคู่ และไม่นับตัวละครที่อายุยังไม่ถึงเกณฑ์ขั้นต่ำ

### บั๊กที่พบระหว่างพัฒนา (แก้ไขแล้วก่อนถือว่าเฟสนี้เสร็จ)

**1. home-tracker พลาดนับตัวละครที่สร้าง/พักใกล้ที่พักที่เพิ่งสร้างเสร็จ:** เดิม `SettlementDetector`
คำนวณกลุ่มถิ่นฐานใหม่ตาม interval เท่านั้น (ทุก 10 tick) ทำให้มีช่วงเวลาสั้นๆ หลังสร้างที่พักเสร็จที่ที่พักนั้น
ยังไม่ถูกจัดเข้ากลุ่มถิ่นฐานใดเลย ถ้าตัวละครสร้างเสร็จแล้วเดินจากไปทำอย่างอื่นทันที (เช่นไปหาอาหารเพราะหิว
กว่า) ก่อนจะกลับมาพัก/สร้างใกล้ที่พักนั้นอีกครั้ง จะไม่ถูกนับเป็นสมาชิกถิ่นฐานนั้นเลยตลอดไป (เจอจริงตอนรัน
`demo:society` ครั้งแรก: ถิ่นฐานหนึ่งมีที่พัก 2 หลังแต่สมาชิก 0 คน) — แก้โดยให้ `SettlementDetector` คำนวณ
ใหม่ทันทีเมื่อจำนวนที่พักในโลกเปลี่ยน ไม่ต้องรอครบ interval (ยังคง interval ไว้เป็นตัวสำรองด้วย)

**2. ตัวละครที่เพิ่งเกิดจับคู่กับพ่อ/แม่ตัวเองทันที เกิดลูกวนไม่หยุด:** ตัวละครใหม่เกิดมาด้วย needs เต็ม 100
ทุกด้าน (ค่า default ปกติของ `Character`) อยู่ตำแหน่งเดียวกับพ่อ/แม่พอดี ทำให้ผ่านเงื่อนไข "ใกล้กัน + social
สูง" ของระบบขยายเผ่าพันธุ์ทันทีที่เกิด และไปจับคู่กับพ่อ/แม่ตัวเองสร้างลูกต่อไปเรื่อยๆ (ตรวจพบตอนเขียน unit
test: ตั้งใจทดสอบว่า cooldown ต่อคู่ทำงาน กลับได้ลูก 18 คนใน 20 tick แทนที่จะเป็น 1) — แก้โดยเพิ่ม field
`bornAtTick` และเงื่อนไขอายุขั้นต่ำ `REPRODUCTION_MIN_AGE_TICKS` (100 tick) ก่อนตัวละครจะเป็นคู่ขยายเผ่าพันธุ์
ได้ ตัวละครที่สร้างตรงๆ ตอนเริ่มโลกถือว่า `bornAtTick = 0` (โตแล้วตั้งแต่ต้น) จึงไม่กระทบตัวละครชุดแรก

### ผลตรวจสอบระยะยาว (รัน `scripts/long-run.js` 30 ปี ตัวละครตั้งต้น 9 ตัว)

**ปัญหาที่พบระหว่าง tune:** ค่าเริ่มต้นของเงื่อนไขขยายเผ่าพันธุ์ที่ลองก่อน (`REPRODUCTION_TICKS_REQUIRED=30`,
`REPRODUCTION_COOLDOWN_TICKS=365`, `MAX_POPULATION=40`) ทำให้ประชากรพุ่งจาก 9 เป็น 40 ตัว (ชนเพดาน) ภายใน
5 ปีแรกเท่านั้น เร็วเกินไปสำหรับโลก 40x40 ที่ทรัพยากรถูก tune ไว้สำหรับ ~9 ตัวละครเดิม ผลคือเกิด flag
"AI มีปัญหา" กับตัวละครจำนวนมาก (9-15 ตัวจาก 40 ตัว) ตั้งแต่ปีที่ 10 เป็นต้นไป เพราะแย่งทรัพยากรกันจนบางตัว
หิว/พลังงาน/สังคมค้างต่ำต่อเนื่อง — ปรับเป็น `REPRODUCTION_TICKS_REQUIRED=300`,
`REPRODUCTION_COOLDOWN_TICKS=1095`, `MAX_POPULATION=15` แล้วประชากรโตแบบค่อยเป็นค่อยไป (9->13->15 ตัวใน
10 ปีแรกแล้วคงที่ที่เพดาน) ไม่มี flag ขึ้นเลยตลอด 30 ปี (รายละเอียดเหตุผลการเลือกค่าอยู่เป็นคอมเมนต์ใน
`src/society/settlement-config.js`)

**ผลตรวจสอบสุดท้าย:**
- ประชากร: 9 -> 13 (ปีที่ 5) -> 15 (ปีที่ 10 ขึ้นไป คงที่ที่เพดาน)
- ถิ่นฐาน: คงที่ 3 ถิ่นฐานตลอดตั้งแต่ปีที่ 5 (สมาชิก 8, 4, 3 คนตามลำดับ)
- **ผู้นำเปลี่ยนมือจริงในการรันปกติ (ไม่ต้องบังคับ)** — ถิ่นฐาน #1: ผู้นำเปลี่ยนจาก #8 เป็น #6 ระหว่างปีที่
  10-15, ถิ่นฐาน #3: เปลี่ยนจาก #5 เป็น #1 ระหว่างปีที่ 5-10 (สร้างที่พักแซงหน้ากันจริงตามธรรมชาติ)
- ที่พักสะสม 115 หลังใน 30 ปี จากตัวละคร (สูงสุด) 15 ตัว (~7.7 หลัง/ตัวละคร ใกล้เคียงเป้าหมายเดิมจากเฟส
  3-แก้ไข ที่ ~6.6 หลัง/ตัวละคร แม้จะมีตัวละครเพิ่มจากการเกิดใหม่ก็ตาม)
- flag "AI มีปัญหา" ไม่ขึ้นเลยตลอด 30 ปี

environment variable `GOOGLE_DRIVE_CREDENTIALS` (JSON string) เท่านั้น ไม่มีการ hardcode หรือเขียนคีย์
ลงไฟล์ใดๆ ในโค้ดหรือ commit

รองรับ credential ได้ 2 รูปแบบ โดยเลือก auth ให้ถูกอัตโนมัติจาก field `"type"` ในตัว credential เอง:
- **`service_account`** — คีย์ของ service account (ของเดิม เหมาะกับ Google Workspace ที่ใช้ Shared Drive ได้)
- **`authorized_user`** — OAuth2 client_id/client_secret/refresh_token (สำหรับบัญชี Gmail ส่วนตัวที่ไม่มี
  Shared Drive ให้ใช้ — เป็นค่าปัจจุบันของโปรเจกต์นี้)

ถ้า field `type` เป็นค่าอื่นที่ไม่รู้จัก หรือ credential ขาด field ที่จำเป็นของแต่ละรูปแบบ ระบบจะโยน error
ข้อความชัดเจนบอกว่าขาดอะไร (ถูก `saveSnapshot` ครอบ try/catch ไว้อีกชั้นเพื่อไม่ให้เกมล่ม)

Snapshot object ประกอบด้วย field ตามสเปกในข้อ 6 ของ `docs/work-instruction.md` เป็นอย่างน้อย:
`timestamp`, `gameYear`, `worldState` (tick, ขนาด grid, ทรัพยากรทุกจุดบน grid, สิ่งก่อสร้างทั้งหมด)
และ `characterCount` — ส่วนข้อมูลตัวละครสรุปแบบสั้นๆ พอ (id, ตำแหน่ง, needs ปัดทศนิยม, inventory,
พฤติกรรมปัจจุบัน) ไม่เอา field ภายในทุกตัว เพื่อไม่ให้ไฟล์ใหญ่เกินจำเป็น

ไฟล์จะถูกอัปโหลดเข้าโฟลเดอร์ `/freeworld-ecosystem/snapshots` บน Drive ชื่อไฟล์รูปแบบ
`snapshot_YYYY-MM-DD_HHmm.json` (เวลาแบบ UTC) ถ้าโฟลเดอร์ตามลำดับยังไม่มีอยู่จริงจะสร้างให้อัตโนมัติ
การบันทึกจะถูกเรียกอัตโนมัติทุกครั้งที่เวลาในเกมผ่านไปครบ 1 ปี โดยผูกกับ `world.tick` ที่มีอยู่แล้ว
(ไม่ต้องแก้ `World` class) ผ่าน `SnapshotScheduler`

ทุกจุดที่คุยกับ Google Drive API ถูกครอบด้วย try/catch: ถ้า credential ผิด รูปแบบไม่ถูกต้อง หรือ
Drive API error (เช่น permission ไม่พอ) จะ log ข้อความที่เข้าใจง่ายแล้วคืนค่า `{ success: false, error }`
**ไม่ throw ออกไป** เพื่อไม่ให้เกมทั้งตัวล่ม

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/storage/
  drive-client.js       -> อ่าน credential จาก env, เลือก auth (service_account / authorized_user)
                             ตาม field "type" อัตโนมัติ, สร้าง Google Drive client,
                             ensureFolderPath หา/สร้างโฟลเดอร์ตามลำดับ path อัตโนมัติ
  snapshot.js             -> buildSnapshot ประกอบ object ตามสเปก, formatSnapshotFilename ตั้งชื่อไฟล์
  save-snapshot.js          -> saveSnapshot: ประกอบ snapshot + อัปโหลดขึ้น Drive พร้อม error handling
                                 (รับ deps แบบ inject ได้เพื่อ mock ตอน test)
  snapshot-scheduler.js       -> SnapshotScheduler: เรียก saveSnapshot อัตโนมัติทุกครั้งที่ครบ 1 ปีเกม
  demo.js                       -> สคริปต์สาธิตจำลอง 3 ปี ใช้ credential จริงจาก env ยืนยันการเชื่อมต่อ Drive
```

`npm test` ของเฟส 5 ตรวจสอบว่า:
- `formatSnapshotFilename` ตั้งชื่อไฟล์ตรงตามรูปแบบ `snapshot_YYYY-MM-DD_HHmm.json` ครบทุกกรณี (รวมเติม 0 นำหน้า)
- `buildSnapshot` ประกอบ object ครบตามสเปก มี `timestamp` / `gameYear` / `worldState` / `characterCount`
  และสรุปข้อมูลตัวละครแบบย่อถูกต้อง
- `saveSnapshot` อัปโหลดผ่าน mock Drive client ได้ถูกต้อง (ตั้งชื่อไฟล์ถูก, เนื้อหาไฟล์ตรงกับ snapshot ที่ประกอบไว้)
  โดยไม่ยิง API จริง
- `saveSnapshot` จัดการ error โดยไม่ throw ทั้งกรณี Drive API ล้มเหลว และกรณีไม่มี/credential ผิดรูปแบบ
- `getDriveClient` สร้าง client ได้ถูกต้องทั้ง 2 รูปแบบ credential (`service_account` และ `authorized_user`)
  และโยน error ข้อความชัดเจนเมื่อ `authorized_user` ขาด field ที่จำเป็น หรือ `type` เป็นค่าที่ไม่รู้จัก
- `ensureFolderPath` หาโฟลเดอร์เดิมถ้ามีอยู่แล้ว หรือสร้างใหม่ตามลำดับ path ถ้ายังไม่มี
- `SnapshotScheduler` เรียก `saveSnapshot` อัตโนมัติทุกครั้งที่ `world.tick` ผ่านไปครบ 1 ปีเกมพอดี

## เฟส 6 — สกุลเงิน xcoin (เสร็จแล้ว)

เพิ่มระบบเศรษฐกิจ xcoin ตามนิยามในข้อ 3 ของ `docs/work-instruction.md`: ทุกตัวละครมี wallet เก็บยอด xcoin
และมีอัตราเงินเฟ้อสุ่ม 2-10% ต่อปีเกม เฟส 7 (ระบบแลกเปลี่ยน) และเฟส 9 (อาชีพที่เกิดเอง) ยังไม่ถูกสร้าง จึง
ต้องตัดสินใจออกแบบเองหลายจุดตามที่สั่งไว้ อธิบายเหตุผลแต่ละจุดด้านล่าง

### การตัดสินใจออกแบบและเหตุผล

**1. เงินเฟ้อ implement เป็น "ดัชนีราคาสะสม" ไม่ใช่ตัวคูณราคาสินค้า:** เพราะยังไม่มีสินค้า/บริการให้อ้างอิง
ราคาจริง (รอเฟส 7/9) จึงยังคูณราคาอะไรไม่ได้จริงๆ `InflationTracker` (`src/economy/inflation.js`) เก็บ
`cumulativeIndex` เริ่มที่ 1.0 แล้วคูณด้วย `(1 + อัตราเงินเฟ้อปีนั้น)` ทบต้นทุกปี (เหมือนดัชนี CPI ในโลกจริง)
**ไม่ได้หักลบยอด xcoin ใน wallet ตรงๆ** — wallet balance ยังคงเพิ่มขึ้นได้อย่างเดียวในเฟสนี้ (ยังไม่มีทาง
ใช้จ่ายจริง) เมื่อเฟส 7/9 มีราคาสินค้า/ค่าจ้างจริงแล้ว ค่อยเอาราคาที่ตั้ง ณ ตอนนั้นหารด้วย `cumulativeIndex`
เพื่อคำนวณมูลค่าจริงได้ทันที ไม่ต้องรื้อโครงสร้างนี้ใหม่

**2. xcoin เป็นสกุลเงินเดียวใช้ร่วมกันทั้งโลก ไม่แยกเศรษฐกิจต่อถิ่นฐาน:** พิจารณาแล้วว่าถ้าแยกดัชนีเงินเฟ้อ
ต่อถิ่นฐาน จะชนกับกลไก merge ถิ่นฐานจากเฟส 4 (เมื่อที่พักใหม่เชื่อม 2 ถิ่นฐานเข้าด้วยกัน จะต้องมีตรรกะรวม
ดัชนีเงินเฟ้อ 2 ชุดเข้าด้วยกันซึ่งซับซ้อนเกินจำเป็นสำหรับเฟสนี้ที่ยังไม่มีการค้าจริง) และ "เงินเฟ้อ" ตามธรรมชาติ
เป็นปรากฏการณ์ระดับสกุลเงิน/ธนาคารกลาง ไม่ใช่ระดับหมู่บ้าน จึงใช้ `InflationTracker` ชุดเดียวสำหรับทั้งโลก
**สิ่งที่ "ผูกกับ settlement" จริงๆ คือมุมมองรายงาน**: `src/economy/settlement-economy.js` มีฟังก์ชัน
`getSettlementTotalBalance`/`getSettlementAverageBalance` ที่รวม/เฉลี่ยยอด xcoin จาก wallet ของสมาชิกใน
ถิ่นฐานนั้นแบบคำนวณสด (derived) ไม่ได้เก็บเป็นบัญชีกลางแยกต่างหาก — เฟส 8 (กฎหมาย) และเฟส 9 (อาชีพ) ที่จะ
ผูกเศรษฐกิจเข้ากับถิ่นฐานจริงๆ (เช่นค่าจ้างขึ้นกับทรัพยากรท้องถิ่น, ผู้นำตั้งภาษี) ยังต่อยอดจากฐานนี้ได้ปกติ

**3. ตัวละครที่เกิดใหม่จากเฟส 4 ได้ `STARTING_BALANCE` เท่าตัวละครตั้งต้น ไม่แยกกรณี:** สเปกบอกว่า "ทุก
ตัวละคร" เริ่มด้วยค่าคงที่นี้ ไม่ได้ระบุข้อยกเว้นสำหรับเด็กเกิดใหม่ การแยกกรณี (เช่นให้เด็กเริ่มที่ 0) จะเพิ่ม
เงื่อนไขที่ไม่มีใครสั่งและยังไม่มีเหตุผลเชิงเกมที่ชัดเจนพอ (phase 6 ยังไม่มี "มรดก" หรือ "ค่าเลี้ยงดู" ให้อ้างอิง)
จึงให้ทุกตัวละครเริ่มเท่ากันไปก่อน ทำใน `Character` constructor (`this.wallet = createWallet()`)

**4. Placeholder "รายได้พื้นฐาน" แทนที่ "การค้า/ทำงาน":** สเปกเฟส 6 บอกว่า "xcoin เกิดจากการค้า/ทำงาน" แต่
ทั้งคู่ยังไม่มีจริง (เฟส 7/9) จึงสร้าง `BasicIncomeGenerator` (`src/economy/basic-income.js`) จ่าย xcoin
จำนวนสุ่มเล็กน้อย (5-20 ต่อปี) ให้ทุกตัวละครทุกปีแทนไปพลางๆ เพื่อให้มี xcoin ไหลเวียนจริงพอทดสอบเงินเฟ้อได้
คอมเมนต์ในไฟล์ระบุชัดเจนว่าเป็น placeholder ที่ควรลบ/ปิดเมื่อเฟส 9 (อาชีพ) เสร็จแล้วให้รายได้มาจากอาชีพจริงแทน

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/economy/
  economy-config.js     -> ค่าคงที่ทั้งหมด (STARTING_BALANCE, ช่วงเงินเฟ้อ, ช่วงรายได้พื้นฐาน)
  wallet.js              -> createWallet/deposit/withdraw (ป้องกันยอดติดลบ)
  inflation.js            -> InflationTracker: สุ่มเงินเฟ้อ 2-10% ทุกปี เก็บเป็น cumulativeIndex ทบต้น
  basic-income.js          -> BasicIncomeGenerator: PLACEHOLDER จ่ายรายได้พื้นฐานสุ่มทุกปี (รอเฟส 9 แทนที่)
  settlement-economy.js      -> รวม/เฉลี่ยยอด xcoin ของสมาชิกแต่ละถิ่นฐานแบบคำนวณสด
  economy-system.js            -> EconomySystem รวม inflation+basicIncome ไว้จุดเดียว เรียก .update(world, characters)
  demo.js                        -> สคริปต์สาธิตยอด xcoin เฉลี่ยต่อถิ่นฐานเปลี่ยนตามปี+เงินเฟ้อ
```

ไฟล์ที่แก้ไขเพิ่ม (อยู่ในขอบเขตงาน เพราะสเปกข้อ 1 บอกว่า "ทุกตัวละครมี wallet" ตรงๆ):
- `src/characters/character.js` — เพิ่ม field `wallet` (สร้างผ่าน `createWallet()` ตอนสร้างตัวละคร)

### วิธีทดสอบ


`npm test` ของเฟส 6 (`tests/economy.test.js`) ตรวจสอบว่า:
- `createWallet` เริ่มต้นด้วย `STARTING_BALANCE` จาก config ได้ถูกต้อง (และ override เองได้)
- `deposit`/`withdraw` แก้ยอดถูกต้อง, `withdraw` ป้องกันยอดติดลบ (ถอนเกินคืนค่า false ไม่แก้ยอด), ทั้งคู่
  โยน error ถ้าได้รับจำนวนติดลบ

  mock `randomFn` และสุ่มจริงด้วย `Math.random` 100 รอบ), และ `cumulativeIndex` ทบต้นถูกต้องข้ามปี

- `getSettlementTotalBalance`/`getSettlementAverageBalance` รวม/เฉลี่ยเฉพาะสมาชิกถิ่นฐานนั้นถูกต้อง
  (ไม่นับตัวละครนอกถิ่นฐาน) และคืนค่า 0 เมื่อไม่มีสมาชิก
- `EconomySystem.update` คืนค่า inflation/income event พร้อมกันเมื่อครบปี และ `null` ทั้งคู่ถ้ายังไม่ครบ

- ยอด xcoin เฉลี่ยของทุกถิ่นฐาน **ไม่เคยติดลบ** (เพิ่มขึ้นต่อเนื่องอย่างเดียวตลอด 30 ปี จาก ~100 เริ่มต้น
  ไปจนถึง ~450-480 ที่ปีที่ 30) เป็นไปตามที่ออกแบบไว้ เพราะเฟสนี้ยังไม่มีทางใช้จ่าย xcoin เลย (รอเฟส 7)
  มีแต่ `deposit` (รายได้พื้นฐาน) ทางเดียว จึงไม่มีทางติดลบได้อยู่แล้วเชิงโครงสร้าง
- ดัชนีราคาสะสมโตขึ้นเป็น **~5.9 เท่า** (เทียบเท่าเงินเฟ้อสะสม ~490%) ภายใน 30 ปี — ตัวเลขนี้ดูสูงเมื่อมองผิวเผิน
  แต่คำนวณถูกต้องตามคณิตศาสตร์การทบต้น: อัตราเฉลี่ยที่สุ่มได้ต่อปีอยู่ราว 6% (กึ่งกลางช่วง 2-10%) ทบต้น 30 ปี
  = `1.06^30 ≈ 5.74` ใกล้เคียงกับผลจริงที่รันได้ ไม่ใช่ค่า NaN/Infinity หรือค่าที่ "ระเบิด" ผิดปกติ จึงถือว่า
  ระบบทำงานสมเหตุสมผลตามที่ออกแบบ (ค่าจะดูสมจริงขึ้นเมื่อเฟส 7/9 เริ่มใช้ `cumulativeIndex` นี้จริง)
- ไม่มีค่า `NaN`/`Infinity`/ยอดผิดปกติใดๆ ตลอดการรัน 30 ปี ทั้งใน wallet และดัชนีเงินเฟ้อ

## เฟส 7 — ระบบแลกเปลี่ยน (เสร็จแล้ว)

เพิ่มระบบแลกเปลี่ยนตามนิยามในข้อ 3 ของ `docs/work-instruction.md`: รองรับทั้งซื้อขายด้วย xcoin และแลก
แบบ barter (ของแลกของ/บริการแลกบริการ) ระหว่างตัวละคร นี่คือจุดแรกที่ `cumulativeIndex` จากเฟส 6 ถูกใช้
คำนวณราคาจริงตามที่ตั้งใจไว้ตอนออกแบบเฟส 6

### การตัดสินใจออกแบบและเหตุผล

**1. ซื้อขายสินค้า (ข้อ 1a): มีแค่ "ไม้" เป็นสินค้าซื้อขายได้ ไม่รวม "อาหาร":** ตรวจสอบโค้ดเฟส 2 แล้วพบว่า
`seekFood()` แปลงอาหารที่เก็บได้เป็นค่า hunger ทันทีในทีเดียว **ไม่เคยเก็บอาหารไว้ใน `inventory` เลย**
(ต่างจากไม้ที่เก็บใน `inventory.wood` จริง) การจะให้ "อาหารส่วนเกิน" ขายได้ต้องแก้ `seekFood()` ให้เก็บอาหาร
เป็น inventory ก่อน ซึ่งเสี่ยงกระทบพฤติกรรมเฟส 2 ที่ทดสอบ/ทำงานอยู่แล้วโดยตรง (ขัดกับเงื่อนไขที่สั่งไว้ว่า
"ต้องไม่ทำให้ Utility AI เดิมของเฟส 2 พังหรือขัดแย้งกัน") จึงเลือกจำกัดสินค้าซื้อขายไว้แค่ไม้ (ทรัพยากรเดียว
ที่มี inventory จริงในปัจจุบัน) ก่อน — เฟส 9 (อาชีพ) ในอนาคตอาจเพิ่มสินค้าประเภทอื่นได้เมื่อมีระบบ inventory
รองรับมากขึ้น

**2. เกณฑ์ "ส่วนเกิน" ของไม้: เกิน `WOOD_SURPLUS_THRESHOLD` (40) หน่วย:** อ้างอิงจากต้นทุนสร้างที่พัก 1 หลัง
(25 หน่วยตามเฟส 3-แก้ไข) บวก buffer ให้เหลือพอสร้างของตัวเองได้อยู่แม้ขายไป 10 หน่วย (`WOOD_TRADE_QUANTITY`)
แล้ว — ในทางปฏิบัติพบว่าด้วยสมดุลเกมปัจจุบัน (shelter decay ต่ำมากจากเฟส 3-แก้ไข) ตัวละครแทบไม่สะสมไม้เกิน
เกณฑ์นี้เลยหลังสร้างที่พักเสร็จ ทำให้ "ซื้อขายไม้" เกิดขึ้นน้อยกว่าบริการมากในทางปฏิบัติ (ดูผลตรวจสอบระยะยาว
ด้านล่าง) แต่ยังเป็นกลไกที่ทำงานถูกต้องเมื่อเงื่อนไขครบ (มี unit test ยืนยัน)

**3. แลกเปลี่ยนบริการ (ข้อ 1b): 2 แบบตามตัวอย่างในสเปก — "จ้างเก็บไม้แทน" และ "จ้างช่วยพัก (ฟื้น energy)":**
ทั้งคู่ resolve ทันทีใน 1 tick (ไม่จำลองให้ helper เดินไปทำงานจริงหลาย tick) เพื่อความง่าย สอดคล้องกับที่
ระบบอื่นในเกมนี้ (build/harvest) ก็ resolve ทันทีเช่นกัน "จ้างเก็บไม้แทน" ให้ helper เก็บไม้จากทรัพยากรจริง
ในโลก (ไม่ได้งอกมาจากอากาศ) แล้วยกให้ buyer

**4. กฎ "ไม่แข่งกับการเอาตัวรอด": ต้องไม่วิกฤต (< 20) และ hunger ต้องปลอดภัยพอ (>= 50) ทั้งสองฝ่าย:**
ตอนแรก implement แค่เงื่อนไข "ไม่วิกฤต" ตามตัวอักษรของสเปก แต่รันจริง 30 ปีด้วย `scripts/long-run.js` แล้ว
เจอ flag "AI มีปัญหา" ใหม่ — วินิจฉัยแล้วพบว่าบริการ "ช่วยพัก" (energy_help) ทำให้ตัวละครไม่ต้องพัก (rest)
เองอีกต่อไป ปลดปล่อยเวลาไปทุ่มกับการหาอาหารเยอะขึ้นพร้อมกันหลายตัว จนแย่งทรัพยากรอาหารที่มีจำกัดกันเอง
รุนแรงขึ้น (ดูรายละเอียดการวินิจฉัยในหัวข้อถัดไป) จึงเพิ่มเงื่อนไขเข้มกว่าเดิมเฉพาะ hunger (เพราะ hunger ลด
เร็วที่สุดและมีลำดับความสำคัญสูงสุด) ว่าต้อง **ไม่ต่ำกว่า 50 ด้วย** ไม่ใช่แค่ไม่วิกฤต (20) เท่านั้น ก่อนจะ
อนุญาตให้ทำธุรกรรมได้เลย — แก้ปัญหาได้สมบูรณ์ (ดูผลตรวจสอบด้านล่าง)

**5. Barter (ข้อ 2): ใช้ "social" แทนเงินเสมอเมื่อ buyer จ่าย xcoin ไม่ไหว:** เลือก social เป็นสกุล barter
เพราะทุกตัวละครมี social ให้ "จ่าย" เสมอไม่ว่าจะรวยหรือจนแค่ไหน (ไม่ต้องมีทรัพยากรพิเศษเหมือนของแลกของ)
และเข้ากับธีม "ช่วยเหลือกันในชุมชน" ตามธรรมชาติ — เงื่อนไขเลือกวิธีจ่าย: **ลอง xcoin ก่อนเสมอ ถ้า buyer มี
ไม่พอถึงตกลง barter แทน** (`payment.js`) เป็นเงื่อนไขที่สมเหตุสมผลตรงไปตรงมา ไม่มีทางล้มเหลว (barter ทำได้
เสมอ ไม่มีเงื่อนไขเพิ่มเติม) ตัวละครจึงเลือกวิธีไหนก็ได้ตามสถานการณ์ทางการเงินของตัวเองจริงๆ ตามที่สั่งไว้

โครงสร้างไฟล์ที่เกี่ยวข้อง:

```
src/trade/
  trade-config.js      -> ค่าคงที่ทั้งหมด (ระยะ, threshold, ราคาฐาน, ฯลฯ)
  pricing.js            -> getWoodPrice/getServicePrice: ราคาฐาน x cumulativeIndex จากเฟส 6
  trade-eligibility.js   -> canTransact: เงื่อนไขร่วมของทุกธุรกรรม (ระยะ, ไม่วิกฤต, hunger ปลอดภัยพอ)
  payment.js               -> settlePayment: ลอง xcoin ก่อน ไม่พอค่อย barter (ฟื้น social แทน)
  goods-trade.js             -> tryTradeWood: ซื้อขายไม้ส่วนเกิน
  service-trade.js             -> tryHireGatherWood / tryHireEnergyHelp: จ้างบริการ 2 แบบ
  trade-system.js                -> TradeSystem รวมทุกอย่างเป็นจุดเดียว เรียก .update(world, characters, cumulativeIndex)
  demo.js                          -> สคริปต์สาธิตธุรกรรมทั้ง 3 รูปแบบพร้อมราคาที่เปลี่ยนตามเงินเฟ้อ
```

ไม่ได้แก้ `behaviors.js`/`utility-ai.js` เลย — เหมือนเฟส 4/6 ระบบแลกเปลี่ยนสังเกต `character.needs`/
`character.position`/`character.wallet`/`character.inventory` จากภายนอกแทน ไม่ต้องผูก dependency
ข้ามโมดูลเข้าไปใน core AI

### วิธีทดสอบ

```bash
npm run demo:trade # สาธิตธุรกรรมทั้ง 3 รูปแบบ (ซื้อขายไม้ด้วยเงิน, แลกไม้แบบ barter, จ้างบริการด้วยเงิน)
npm test            # รวม unit test ของเฟส 1-4, 6-7 (ใช้ node:test)
```

`npm test` ของเฟส 7 (`tests/trade.test.js`) ตรวจสอบว่า:
- `getWoodPrice`/`getServicePrice` คูณราคาฐานด้วย `cumulativeIndex` ถูกต้อง
- `canTransact` ปฏิเสธเมื่ออยู่ไกลเกินระยะ, ฝ่ายใดฝ่ายหนึ่งวิกฤต, หรือ hunger ต่ำกว่าเกณฑ์ safety (แม้ยัง
  ไม่ถึงเกณฑ์วิกฤตก็ตาม)
- `tryTradeWood` ซื้อขายด้วย xcoin คำนวณราคาตามดัชนีเงินเฟ้อถูกต้องและ wallet ไม่ติดลบ, แลกแบบ barter
  (โอนไม้ + ฟื้น social ทั้งคู่) เมื่อ xcoin ไม่พอ, ไม่เกิดธุรกรรมถ้า buyer ไม่ต้องการ/seller ไม่มีส่วนเกิน/
  ฝ่ายใดฝ่ายหนึ่งวิกฤต
- `tryHireGatherWood`/`tryHireEnergyHelp` ทำงานถูกต้องทั้ง xcoin และ barter, เก็บไม้จากทรัพยากรจริงในโลก
  (ไม่ใช่งอกจากอากาศ), ปฏิเสธเมื่อ buyer hunger ต่ำกว่าเกณฑ์ safety
- `TradeSystem.update` นับจำนวนธุรกรรมแยกประเภท xcoin/barter สะสมถูกต้อง และไม่ให้ตัวละครเดียวทำธุรกรรม
  ซ้ำในรอบเดียว

### บั๊กที่พบระหว่างพัฒนา (แก้ไขแล้วก่อนถือว่าเฟสนี้เสร็จ)

รันจริง 30 ปีด้วย `scripts/long-run.js` (ตามข้อ 5 ของสเปก) รอบแรกพบ flag "AI มีปัญหา" ใหม่ที่ไม่เคยมีมาก่อน
เพิ่มขึ้นมา วินิจฉัยด้วยการรันเปรียบเทียบแยกทีละกลไก (goods เท่านั้น / gather_wood เท่านั้น / energy_help
เท่านั้น) พบว่า **เฉพาะบริการ "ช่วยพัก" (energy_help) เท่านั้น** ที่ทำให้เกิด flag — สาเหตุคือ energy_help
ฟื้น energy ให้ทันทีโดยไม่ต้องพัก (rest) จริง ทำให้ตัวละครไม่มีเหตุผลต้องหยุดพักอีกต่อไป จึงทุ่มเวลาทั้งหมดไป
กับการหาอาหารแทน (เพราะ hunger ยังเป็น need ที่ลดเร็วที่สุด) หลายตัวพร้อมกัน จนแย่งทรัพยากรอาหารที่มีจำกัด
และงอกใหม่ช้ากันเองรุนแรงขึ้นกว่าตอนไม่มี trade — บางตัวโชคร้ายไปเจอช่วงที่ทรัพยากรแถวนั้นหมดพอดีติด flag

ลองแก้ด้วยการเพิ่ม cooldown ต่อคู่สำหรับบริการก่อน (กันคู่เดิมจ้างกันซ้ำถี่) แต่รันจริงแล้ว **กลับแย่ลง**
(cooldown เปลี่ยนจังหวะว่าใครได้ทำธุรกรรมในแต่ละ tick ซึ่งบังเอิญไปกระทบจังหวะการหาอาหารของตัวละครอื่นแทน)
จึงตัดกลไก cooldown ออก แล้วแก้ที่รากปัญหาจริงแทน: เพิ่มเงื่อนไข `HUNGER_SAFETY_THRESHOLD` (50) ใน
`canTransact` ให้ทั้งสองฝ่ายต้อง hunger ไม่ต่ำกว่าเกณฑ์นี้ก่อนทำธุรกรรมได้ (เข้มกว่าเกณฑ์วิกฤตทั่วไปเฉพาะ
hunger เพราะเป็น need ที่ลดเร็วที่สุดและสำคัญที่สุด) ป้องกันไม่ให้ตัวละครไปมัวทำธุรกรรมตอน hunger กำลังจะ
ลดลงจนพลาดจังหวะไปหาอาหาร — วิธีนี้แก้ปัญหาได้สมบูรณ์โดยไม่ต้องมี cooldown เพิ่ม

ระหว่างวินิจฉัยยังพบด้วยว่า `scripts/long-run.js` ไม่ deterministic ข้ามการรัน เพราะ `InflationTracker`/
`BasicIncomeGenerator` จากเฟส 6 ใช้ `Math.random()` จริงโดย default (ไม่ได้ฉีด seed เหมือนที่ `World`/
`Character` ทำ) ทำให้ผลแต่ละรอบต่างกันแม้ config เดิมทุกอย่าง — ถือเป็นช่องโหว่เล็กๆ ที่ตกหล่นมาตั้งแต่
เฟส 6 ซึ่งทำให้การเปรียบเทียบผลก่อน/หลังแก้บั๊กไม่น่าเชื่อถือเท่าที่ควร จึงฉีด `createRng` (ตัวเดิมจาก
`src/world/random.js` ที่ `World` ใช้อยู่แล้ว) เข้าไปแทนใน `scripts/long-run.js` ให้ผลรันซ้ำได้เหมือนเดิม
ทุกครั้งตามหลักการเดิมของสคริปต์นี้ (ไม่ได้แก้ไฟล์ `src/economy/*` เพราะ default `Math.random()` ยังเหมาะสม
สำหรับการใช้งานจริง/demo ทั่วไป เปลี่ยนแค่จุดที่ต้องการ reproducibility สำหรับเครื่องมือตรวจสอบนี้)

### ผลตรวจสอบระยะยาว (รัน `scripts/long-run.js` 30 ปี ตัวละครตั้งต้น 9 ตัว, deterministic)

- **ไม่มี flag "AI มีปัญหา" เลยตลอด 30 ปี** (ยืนยันซ้ำหลายรอบ ผลลัพธ์เหมือนเดิมทุกครั้งเพราะ deterministic แล้ว)
- ธุรกรรมสะสมถึงปีที่ 30: xcoin 88 ครั้ง, barter 18 ครั้ง (รวม 106 ครั้งใน 30 ปี กับตัวละครสูงสุด 12 ตัว)
  ส่วนใหญ่เป็นบริการ (จ้างเก็บไม้แทน/ช่วยพัก) เพราะไม้ส่วนเกินสะสมถึงเกณฑ์ขายได้ไม่บ่อยนักตามที่อธิบายไว้
  ข้างต้น (ข้อ 2)
- ประชากรโตค่อยเป็นค่อยไป 9 -> 11 -> 12 ตัว คงที่ที่ 12 ตั้งแต่ปีที่ 15 (สอดคล้องกับที่ tune ไว้ในเฟส 4)
- ถิ่นฐานคงที่ 3 ถิ่นฐานตลอด เห็นผู้นำถิ่นฐาน #1 เปลี่ยนมือตามธรรมชาติ 2 ครั้ง (#3 -> #4 -> #2) ระหว่างทาง
- ยอด xcoin เฉลี่ยต่อถิ่นฐานโตต่อเนื่องไม่มีติดลบ (จาก ~150-170 ปีที่ 5 ไปจนถึง ~440-500 ปีที่ 30)
- ดัชนีราคาสะสมโตเป็น ~5.1 เท่า (~413.5%) ภายใน 30 ปี ใกล้เคียงกับที่คาดไว้ในเฟส 6
